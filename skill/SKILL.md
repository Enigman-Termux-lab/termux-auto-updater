# Auto Updater

Если приложение не удаётся классифицировать или после обновления нужен ремонт
окружения, используй `termux-fix-path`. Скилл `auto-updater` отвечает за
обнаружение доступных обновлений и инициацию процесса, но при выполнении обновлений
и после них ОБЯЗАН строго следовать стандартам `termux-fix-path` (цепочка:
launcher → runtime → ELF → shebang → glibc-runner → очистка устаревших обёрток
в `~/.local/bin/` → валидация запуска).

Этот скилл содержит скрипт и инструкции для безопасного обновления приложений и пакетов именно в Termux/Android.

Скилл не должен запускаться как обычный Linux-скрипт: Termux использует Android/Bionic, а не стандартный Linux/glibc.

## Обязательный порядок

1. Определить, что текущая среда — Termux (`$PREFIX`, `pkg`, `apt-get`). В другой среде завершить работу.
2. Найти доступные обновления через поддерживаемые менеджеры и показать пользователю список.
3. Показать Termux-рекомендации и риски.
4. Запросить явное разрешение. Без интерактивного подтверждения ничего не обновлять.
5. Для найденных pip-пакетов запросить отдельное подтверждение: pip может перезаписать пакеты, которыми управляет `pkg`.
6. Выполнить согласованные обновления пакетов и менеджеров.
7. После обновления строго следовать регламенту `termux-fix-path`:
   - Проверить наличие перехватывающих обёрток в `~/.local/bin/` для обновленных системных пакетов из `$PREFIX/bin` (Модуль 7 `termux-fix-path`), деактивировать их с архивацией в `~/.local/state/backups/` и сбросить кэш `hash -r`;
   - Восстановить Termux shebang (`termux-fix-shebang`) для всех глобальных CLI в `$(npm prefix -g)/bin` (только для текстовых скриптов, никогда для ELF);
   - Проверить цепочку launcher → runtime → ELF → glibc-runner;
   - Проверить валидацию запуска (`--version` / `--help`) доверенных CLI;
   - При сбоях — следовать регламенту безопасного восстановления по Модулю 9 `termux-fix-path`;
   - Только при полном отсутствии ошибок (`ERRORS == 0`) записать timestamp успешного запуска.

## Поддерживаемые источники обновлений

Скилл не привязан к фиксированному набору приложений: он сначала обнаруживает
доступные менеджеры и применяет только подходящий для найденного источника.

1. **Termux `pkg`/`apt`**: системные и установленные из репозиториев Termux-пакеты.
2. **Глобальный NPM**: глобальные Node.js-приложения и модули, включая Codex CLI.
3. **Python/pip**: устаревшие Python-пакеты, если `pip` установлен.
4. **uv**: установленные через `uv tool` приложения.
5. **Self-updater приложения**: поддержанные отдельные обновляторы, например `agy update`.

Приложения, установленные standalone-архивом, Linux-бинарником, APK или неизвестным
установщиком, не обновляются угадыванием. Скилл показывает предупреждение и требует
отдельного адаптера/команды. Это сохраняет универсальность без опасного
`update-everything`.

## Что обновляется:
1. **Пакеты Termux**: После подтверждения выполняются `apt-get update` и `apt-get upgrade` в неинтерактивном режиме с сохранением существующих конфигов.
2. **NPM модули и Codex CLI**: обновляются глобальные NPM-пакеты, включая `@mmmbuto/codex-cli-termux`.
3. **Python/pip и uv tools**: обновляются только обнаруженные устаревшие пакеты/инструменты; pip требует отдельного подтверждения из-за риска конфликта с `pkg`.
4. **Claude Code**: пакет `@anthropic-ai/claude-code` исключается из `npm update -g` и не переустанавливается.
5. **Antigravity CLI**: после общего разрешения запускается `agy update`; сам `agy` дополнительно проверяет доступность новой версии и спрашивает перед применением.

## Termux-совместимость

- Нативные Termux-пакеты устанавливаются через `pkg`/`apt`, а не через Linux-установщики.
- Обычные glibc-бинарники Android напрямую не запускает. Для них нужен `glibc-runner`; наличие runner’а проверяется до обновления.
- Если приложению нужен glibc, рекомендуемый Termux-путь: подключить `glibc-repo`, установить `glibc`, затем запускать бинарник через `glibc-runner`. Это отдельная операция и не выполняется автоматически.
- В Termux нет `/usr/bin/env` в обычном Linux-смысле. После обновления NPM CLI скилл запускает `termux-fix-shebang` для всех установленных глобальных CLI в `$(npm prefix -g)/bin` (только для текстовых скриптов, никогда для ELF).
- Если `agy` падает после обновления, скилл только показывает рекомендацию `pkg reinstall -y glibc`; сам ремонт без отдельного подтверждения не выполняется.
- Переустановка пакетов, исправление shebang’ов и обновление приложений — разные действия; согласие на одно не следует молча распространять на другие.

## Регламент интеграции с termux-fix-path

`auto-updater` отвечает за обнаружение доступных обновлений и инициацию процесса, но при выполнении обновлений и после них ОБЯЗАН строго следовать стандартам `termux-fix-path`:

1. **Цепочка проверки:** `launcher` → `runtime` → `ELF` → `shebang` → `glibc-runner` → `очистка устаревших обёрток в ~/.local/bin/` → `валидация запуска`.
2. **Очистка устаревших обёрток (Модуль 7 `termux-fix-path`):**
   - При обновлении пакетов через `pkg`/`apt` проверить системный `PATH`: доступна ли нативная версия в `$PREFIX/bin/$APP`.
   - Если в `~/.local/bin/$APP` находится старый launcher/wrapper, он может перехватывать вызов из-за приоритета `~/.local/bin` в `$PATH`.
   - Проверить прямой запуск `$PREFIX/bin/$APP --version` (или `--help`). Если нативная версия работает штатно, деактивировать устаревшую обёртку перемещением в `~/.local/state/backups/` и сбросить кэш оболочки `hash -r`.
3. **Изолированное хранение бэкапов:**
   - Все резервные копии и старые лаунчеры сохранять строго в `~/.local/state/backups/`.
   - Категорически запрещено оставлять бэкапы или архивы прямо в `~/.local/bin/` или других папках из `$PATH`.
4. **Обработка shebang (Модуль 2 `termux-fix-path`):**
   - Обрабатывать все текстовые скрипты-лаунчеры в `$(npm prefix -g)/bin` и внутренние бинарники модулей.
   - Никогда не применять `termux-fix-shebang` к ELF-бинарникам.
5. **Валидация запуска:**
   - Проверять запуск (`--version` / `--help`) только у доверенных установленных программ (`codex`, `agy`).

## Безопасное восстановление при сбоях (Модуль 9 termux-fix-path)

Если после обновления CLI или пакет перестает запускаться:
- **Категорический запрет:** не запускать повторное массовое обновление «вслепую», не удалять `$PREFIX` и не переустанавливать среду Termux.
- **Порядок восстановления по Модулю 9:**
  1. Зафиксировать ошибку из лога (`/tmp/auto_update_*.log`), вывод `command -v`, `file`, `readlink -f` и `readelf -l` (`PT_INTERP`).
  2. Определить, какой файл обновился и какому менеджеру/пакету он принадлежит.
  3. Восстановить файл из проверенного бэкапа в `~/.local/state/backups/` либо через штатную переустановку пакета (`pkg reinstall <пакет>`).
  4. Для текстовых launcher применить `termux-fix-shebang`.
  5. Для glibc приложений (например, `agy`) проверить доступность `glibc-runner` и предложить переустановку glibc (`pkg reinstall -y glibc`).
  6. Провести проверку запуска доверенного CLI (`--version` / `--help`).
  7. Сообщить пользователю путь к бэкапу, результат восстановления и остаточные ограничения.

## Скрипт
`/data/data/com.termux/files/home/.agents/skills/auto-updater/scripts/update_all.sh`

Скрипт проверяет файл `last_update.timestamp` в папке скилла. Если с момента последнего успешного обновления прошло менее 7 дней, скрипт досрочно завершается со статусом `UPDATE_SKIPPED`, чтобы не выполнять лишние операции.
Если обновление запускается, скрипт собирает логи в `/tmp/auto_update_<дата>.log` и возвращает `UPDATE_SUCCESS` (перезаписывая timestamp) или `UPDATE_FAILED`.

## Автоматизация

Скрипт сохраняет недельный cooldown через `last_update.timestamp`, но фоновый или
неинтерактивный запуск без разрешения пользователя запрещён. Внешний scheduler
может только запустить проверку; обновление без интерактивного подтверждения будет
остановлено со статусом `UPDATE_NEEDS_APPROVAL`.
